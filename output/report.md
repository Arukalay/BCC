- **R-44.2 · Существенно · полнота.** Не описан результат при нарушении каждой из проверок: какой ответ возвращается при неверной сумме и какой — при неверном значении переключателя. Без этого в методе остаётся неописанная ветка ошибки.
  - Как исправить: Добавить поведение для ошибок, например: «При неверном `amount` или `enabled` метод возвращает 400 и сообщение `Некорректный запрос`; при корректных значениях переходит к сохранению».
- **R-44.3 · Замечание · атомарность.** В одном пункте объединены две отдельные проверки: суммы и переключателя. Это мешает отдельно принять или отклонить каждое правило и разнести тесты по двум независимым условиям.
  - Как исправить: Разбить на два пункта: «Проверить сумму» и «Проверить переключатель».

### R-45 · Заменить настройку и вернуть результат

Раздел: Часть B. REST API / Логика работы метода

- **R-45.1 · Существенно · непротиворечивость.** Внутри метода не согласованы действия с логикой ответа: в разделе статусов для успешного случая указан ответ «200. Successful — Created», что по смыслу относится к созданию, а здесь описано именно замещение существующей настройки. Из-за этого реализация может выбрать неверный статус или семантику ответа.
  - Как исправить: Уточнить семантику успешного ответа для операции замены, например: «Заменить настройку и вернуть результат сохранения с кодом 200».
- **R-45.2 · Существенно · полнота.** Не определено, что именно считать «результатом сохранения»: какой состав полей должен вернуться, в каком статусе, и что делать при частично успешной записи. Без этого нельзя однозначно реализовать и проверить ответ метода.
  - Как исправить: Дополнить формулировку: «Заменить настройку, затем вернуть HTTP 200 и тело ответа с полями result=OK, amount, enabled; при неуспехе вернуть HTTP 400/500 и тело ошибки».

### R-46 · При ошибке суммы вернуть прежнее состояние и ERROR

> `5. При отклонении суммы вернуть прежнее состояние и результат ERROR.`

Раздел: Часть B. REST API / Логика работы метода

- **R-46.1 · Существенно · однозначность.** Термин «отклонении суммы» не определяет, какие именно значения считаются отклонёнными: только вне диапазона, нецелые, пустые или ещё и неверный тип. Из-за этого одно и то же значение может трактоваться по-разному и приводить к разной реакции сервиса.
  - Как исправить: Заменить на проверяемое условие, например: «При отсутствии суммы, нецелом значении или значении вне диапазона 1 000–1 000 000 вернуть прежнее состояние и результат ERROR».
- **R-46.2 · Существенно · полнота.** Не указано, что именно значит «прежнее состояние»: сохраняются ли старые значения amount и enabled, возвращается ли прежний HTTP-код и какое тело ответа должен получить клиент. Без этого невозможно проверить восстановление состояния после ошибки.
  - Как исправить: Уточнить поведение на ошибке, например: «При отклонении суммы не изменять сохранённую настройку и возвращать HTTP 400 с телом {"result":"ERROR","message":"..."}».

### R-47 · Порог задаётся целым числом тенге в границах

> `1. Целое число тенге, обе границы включены.`

Раздел: Часть B. REST API / Особые правила

- **R-47.1 · Существенно · однозначность.** Фраза не задаёт сами границы диапазона в тексте требования; без чисел невозможно однозначно проверить, какое значение допустимо, а какое нет. В результате реализация может принять разные пределы и тесты будут интерпретировать требование по-разному.
  - Как исправить: Указать диапазон явно, например: «Целое число тенге от 1 000 до 1 000 000 включительно».
- **R-47.2 · Существенно · проверяемость.** Из-за отсутствия конкретных значений границ нельзя составить однозначные тесты на нижнюю и верхнюю границу. Невозможно зафиксировать ожидаемый результат для крайних допустимых значений.
  - Как исправить: Записать числовые границы в самом требовании, например: «Значение суммы — целое число тенге в диапазоне 1 000–1 000 000 включительно».

### R-48 · Повторное сохранение заменяет текущую настройку

> `2. Повторное сохранение заменяет действующую настройку.`

Раздел: Часть B. REST API / Особые правила

- **R-48.1 · Существенно · однозначность.** Неясно, что считается «повторным сохранением»: повтор того же запроса, любое следующее сохранение по той же карте или сохранение после изменения параметров. Из-за этого нельзя однозначно определить, когда должна происходить замена настройки.
  - Как исправить: Уточнить условие, например: «Каждый новый запрос на сохранение настроек по той же карте полностью заменяет ранее сохранённую настройку».
- **R-48.2 · Существенно · полнота.** Не описано, сохраняются ли при замене все поля целиком или только изменённые, а также что происходит с накопленными расходами при замене. Без этого поведение при повторном сохранении остаётся неполным и может быть реализовано по-разному.
  - Как исправить: Дополнить правило, например: «При повторном сохранении по той же карте полностью заменить значения amount и enabled, при этом накопленные расходы не изменять».

### R-53 · Тело запроса имеет Content-Type application/json

> `Content-Type: application/json .`

Раздел: Часть B. REST API / Параметры запроса / Request body

- **R-53.1 · Критично · непротиворечивость.** В строке задан `Content-Type: application/json`, но для запроса одновременно указан метод GET и тело не используется. Для GET-метода JSON-тело не требуется, поэтому указание `Content-Type` создаёт неясность: что именно должно быть отправлено с этим заголовком и должен ли сервер его проверять. Из-за этого разные реализации могут вести себя по-разному.
  - Как исправить: Либо убрать `Content-Type` из раздела Request body, либо заменить метод на такой, который действительно использует тело запроса, и описать состав тела явно.

### R-55 · Разделение ответов на успешные и неуспешные

Здесь неясно, какие именно коды считаются неуспешными и как трактовать коды, не перечисленные в тексте; из-за этого невозможно однозначно реализовать обработку всех ответов.

### R-56 · Поле result показывает OK или ERROR

Раздел: Часть B. REST API / Ответ

В самом фрагменте не сказано, при каких именно исходах допустим `OK`, а при каких `ERROR`, поэтому интерпретация поля зависит от дополнительных предположений.

### R-57 · Поле amount возвращает порог

### R-62 · Пример успешного ответа 200 с OK

- **R-62.3 · Замечание · атомарность.** В одном примере смешаны сразу три независимых признака результата: код HTTP 200, поле result=OK и возврат значений amount/enabled. По одному примеру нельзя отдельно принять или отклонить, какой именно состав успешного ответа обязателен, поэтому при проверке может возникнуть спор, обязателен ли полный набор полей.
  - Как исправить: Разделить контракт на отдельные утверждения: отдельно описать обязательные поля успешного ответа и отдельно привести пример, например: «При успешном выполнении метод возвращает 200 и JSON с полями result, amount, enabled».

### R-63 · Пример 200 с ошибкой проверки суммы

  - Как исправить: Развести коды и тела ответа: либо оставить error-ответ под 400/422, либо явно написать, что HTTP 200 может содержать бизнес-ошибку и тогда это не «Successful», например переименовать блок в «200. Successful / business error».

  - Как исправить: Указать точное правило ошибки, например: «При amount вне диапазона 1 000–1 000 000 возвращается 400 и message="Сумма должна быть от 1000 до 1000000"».
- **R-63.3 · Замечание · атомарность.** Пример одновременно фиксирует и бизнес-результат ERROR, и конкретный текст сообщения. Это два разных требования к ответу, и их лучше описывать отдельно, чтобы можно было независимо проверить код ответа и содержание ошибки.
