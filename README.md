# Агент проверки требований

ИИ-агент для хакатона **BCC-HUB x MNU FinTech**: статически проверяет документ с требованиями (ревью до разработки,
а не запуск тестов) и сам пишет отчёт на русском языке. Агент нарезает документ на отдельные требования, проверяет
каждое и весь набор целиком по критериям **ISO/IEC/IEEE 29148:2018** (п. 5.2.5, 5.2.6) и **IEEE Std 830-1998** (п. 4.3)
и привязывает каждое нарушение к дословной цитате из документа.

## 📄 Отчёт агента

**[`output/report.md`](output/report.md)** — отчёт, который агент сформировал по выданному документу
[`docs/requirements.md`](docs/requirements.md) без ручных правок.

| Паспорт прогона | |
|---|---|
| Документ | `docs/requirements.md` (выдан организаторами, не изменялся) |
| Модель | OpenAI `gpt-5.4-mini` |
| Версия агента | коммит `5d16375` |
| Дата | 27.11.2026 |
| Команда | `python -m validator docs/requirements.md output/report.md` |

**Итог агента:** начинать разработку и тестирование по документу нельзя. Выделено 85 требований, у 44 есть
нарушения; всего 103 нарушения, из них 6 критичных:

- метод описан как GET, хотя сохраняет настройку;
- ответ 200 назван «Created» и содержит вариант с `result=ERROR`;
- успешным назван и код 201, но для него нет описания и примера;
- для Prod нет URL;
- не описано, как запрос передаёт сессию для проверки владельца карты;
- не описано поведение при повторном достижении порога в том же месяце и при смене порога после уже отправленного push.

## Быстрый старт: повторить прогон

```bash
git clone https://github.com/Arukalay/BCC.git && cd BCC
python3.11 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # впишите ключ в .env (раздел 3)
python -m validator docs/requirements.md output/my_report.md
```

Новый отчёт появится в `output/my_report.md`; сданный `output/report.md` при этом не перезаписывается.
Состав находок от прогона к прогону немного меняется (модель недетерминирована), разделы и формат — те же.

## 1. Что нужно

- **Python 3.11+** и **git** (по git агент определяет свою версию для паспорта отчёта).
- Ключ LLM: **OpenAI** (им сформирован сданный отчёт) или бесплатный **Google Gemini** (раздел 3).

## 2. Установка

```bash
python3.11 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Проверяемый документ организаторов уже лежит в `docs/requirements.md` (без изменений). Если его нет:
`curl -sL https://raw.githubusercontent.com/BCC-HUB/ai-requirements-validator-task/main/docs/requirements.md -o docs/requirements.md`

## 3. Ключ LLM: как получить и куда положить

Ключ кладётся в файл `.env` в корне проекта. Шаблон без ключей: `.env.example`. Файл `.env` в git не попадает.

```bash
cp .env.example .env
```

**OpenAI (основной вариант, им сформирован отчёт).** Ключ: <https://platform.openai.com/api-keys> → *Create new secret key*;
на аккаунте нужен положительный баланс (*Billing*). Один прогон стоит несколько центов.

```env
LLM_PROVIDER=openai
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-5.4-mini
```

**Gemini (бесплатно, без оплаты).** Ключ: <https://aistudio.google.com/> → *Get API key* → *Create API key*.

```env
LLM_PROVIDER=gemini
GEMINI_API_KEY=...
GEMINI_MODEL=gemini-3.1-flash-lite
```

Проверить ключ и увидеть модели, доступные на нём: `python -m validator --check-llm`.

## 4. Запуск

Одна команда: путь к документу требований и путь к файлу отчёта.

```bash
python -m validator <путь_к_требованиям> <путь_к_отчёту>
python -m validator docs/requirements.md output/report.md
```

- **Входные форматы:** `.pdf` (с текстовым слоем), `.md`, `.txt`, `.docx`.
- **Куда ляжет отчёт:** по второму пути; папка создаётся, если её нет. Сданный отчёт: [`output/report.md`](output/report.md).
- **Время:** несколько минут, около 20 запросов к модели. Ход работы печатается в консоль, `-v` — подробнее.
- **Коды возврата:** `0` отчёт записан; `2` документ не прочитан; `3` ошибка модели (ключ, квота, баланс,
  недоступность); `4` отчёт не записан; `1` прочее; `130` прервано (Ctrl+C).

Временные сбои API (`429` по минутному лимиту, `5xx`, таймаут 120 с) агент переживает повторами. Ошибки, которые
повтор не исправит (неверный ключ, нет баланса, исчерпана суточная квота, модель недоступна), останавливают прогон
сразу с понятным сообщением.

## 5. Что в отчёте

Отчёт на русском, разделы по ТЗ:

1. **Паспорт прогона:** документ, дата, модель, версия агента (короткий хеш git-коммита; `-dirty`, если код изменён после коммита).
2. **Как агент нарезал требования:** таблица «ID в отчёте — ID в документе — краткая формулировка»; у требований без
   номера в документе — дословная цитата.
3. **Проверка каждого требования:** у требования с нарушениями — его цитата и список нарушений
   (номер, критичность, критерий, в чём проблема, цитата-доказательство, как исправить); требования без замечаний
   перечислены одной строкой.
4. **Проверка набора целиком:** противоречия между пунктами, пробелы, шаблон, термины, прослеживаемость, контракт API,
   сгруппированные по виду.
5. **Сводка:** число требований и нарушений (всего и по критичности), список критичных дефектов по типам из ТЗ:
   непроверяемые, противоречивые, неполные.
6. **Итог:** можно ли начинать разработку и тестирование и что исправить в первую очередь (до 10 пунктов).

Каждое нарушение привязано к цитате. Код проверяет, что цитата действительно есть в документе: неточную просит модель
исправить, иначе находка отбрасывается. Цитаты показываются текстом документа (с его тире и кавычками, без символов
разметки markdown), поэтому их находит поиск по документу. Все числа в сводке и итоговый вывод считает код, а не модель.

## 6. Как работает агент

`loader` читает документ → `pipeline` делает четыре шага через `llm` → `report` собирает отчёт.

1. **Нарезка:** модель выделяет отдельные проверяемые утверждения с дословными цитатами.
2. **Проверка каждого требования** пачками по 4 по десяти критериям: необходимость, однозначность, полнота,
   непротиворечивость, выполнимость, проверяемость, прослеживаемость, отсутствие навязанной реализации, атомарность,
   согласованность терминов.
3. **Проверка набора** в четыре прохода с пошаговой процедурой: согласованность (в том числе пересчёт каждого кейса
   приёмки по правилам и сверка статусов API с примерами), шаблон и ревью, пробелы, приёмка и термины.
4. **Проверка цитат и сборка:** недостоверные цитаты исправляются или отбрасываются, повторы склеиваются, находки
   сортируются по критичности и порядку в документе.

Промпты: `validator/prompts.py`; провайдер модели подменяемый (`LLMClient` в `validator/llm.py`).

## 7. Модель и почему

Сданный отчёт сформирован моделью **OpenAI `gpt-5.4-mini`**. Выбор сделан по сверке с эталоном дефектов
(раздел 8): бесплатные модели Gemini находили меньше половины дефектов и не видели противоречий между пунктами.

| Прогон | Модель | Промпты | Находок | Найдено по смыслу | С частичными | Критичных из 5 |
|---|---|---|---|---|---|---|
| 1 | gemini-3.1-flash-lite | v1.1 | 48 | 21 из 58 (36%) | 29 (50%) | 1 |
| 3 | gemini-3.1-flash-lite | v1.2 | 54 | 25 из 58 (43%) | 37 (64%) | 1 |
| 4 | gpt-5.4-mini | v1.2 | 182 | 39 из 58 (67%) | 49 (84%) | 4 |
| **7, сданный отчёт** | **gpt-5.4-mini** | **v1.6** | **103** | **36 из 58 (62%)** | **44 (76%)** | **4** |

Между прогонами 4 и 7 промпты очищены от подсказок под проверяемый документ, а повторы и составные замечания
убраны: охват почти тот же, отчёт вдвое короче. Подробности — в `tests/evaluation.md`.

Gemini тоже поддерживается (бесплатный вариант по ТЗ). На 27.11.2026 на бесплатном тарифе работают
`gemini-3.1-flash-lite` и `gemini-3.5-flash-lite`; `gemini-2.5-*` недоступны новым ключам, а `gemini-3.5-flash` и новее
дают 20 запросов в сутки на проект, этого не хватает на один прогон.

## 8. Проверка качества

- **Эталон дефектов** `tests/reference_defects.md`: 58 дефектов документа, разобранных вручную, с цитатами. Агенту не
  передаётся, нужен только для сверки.
- **Сверка отчёта с эталоном:** `python tests/compare_reference.py docs/requirements.md output/report.md`. Сверка ищет
  совпадения цитат, поэтому даёт верхнюю оценку; итоговые цифры выше посчитаны по смыслу вручную, итоги и выводы
  прогонов — в `tests/evaluation.md`.
- **Тесты без обращения к модели:** `pytest`. Покрывают чтение форматов, схемы, отчёт, точность цитат, устойчивость
  к сбоям API, клиентов OpenAI и Gemini, весь конвейер и CLI на моке модели (`tests/mock_llm.py`), а также то, что в
  промптах нет слов и подсказок из проверяемого документа.

## 9. Структура

```
validator/        агент: cli, loader, llm (OpenAI, Gemini), pipeline, prompts, report, schemas
docs/             проверяемый документ организаторов (не изменяется)
output/report.md  сданный отчёт агента
tests/            тесты, мок модели, эталон дефектов, сверка с эталоном, оценка прогонов (evaluation.md)
```

## 10. Ограничения

- Результат модели не полностью детерминирован: состав находок от прогона к прогону немного меняется.
- PDF читается через `pypdf`: при извлечении текста таблицы теряют разметку, сканы без текстового слоя не поддерживаются
  (агент сообщит, что нужен OCR).
- Весь документ передаётся модели в каждом запросе; очень большие документы (сотни страниц) потребуют модель с
  большим контекстом.
